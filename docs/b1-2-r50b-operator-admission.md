# B1.2 R50-B: local operator admission candidate

Specification: Draft. Implementation: Partially implemented, local gate tested.
Authority: LOCAL_ONLY. No commit, push, PR, deployment, provider setting change,
secret read/provisioning, live event, browser CTA click or new D1 query is authorized.
Baseline: b34f31a984efa26676c00deae16b904c42fb29c8.

## Scope

The candidate adds an operator-only admission path to the existing `/api/event`
handler while preserving the public client OFF, the 24-route/31-pair matrix,
the existing five-column aggregate schema, Worker, privacy pages and OFF checks.
The request payload remains exactly `event`, `page`, `locale`; the only permitted
trial tuple is `triage_click`, `/agent-authority-audit`, `en`.

A bearer capability establishes possession of a separately approved operator
permit, not the civil identity of Robert or proof of a real human click. No real
token has been generated by these tests; all fixtures are public dummy values.
Browser mounting/interception for an actual owner click is NOT implemented here.
No token belongs in a URL, HTML, logs, Git, a public page, or the Worker envelope.

## Fail-closed admission

The R50 namespace uses six explicit settings, with no enabled defaults:

- `BITEVO_EVENT_COUNTER_R50_MODE=operator-only`
- `BITEVO_EVENT_COUNTER_R50_TRIAL_ID`: canonical UUIDv4 for this trial
- `BITEVO_EVENT_COUNTER_R50_OPERATOR_TOKEN_SHA256`: SHA-256 of the separate 64-hex
  operator token string; not the event signing secret or its digest
- `BITEVO_EVENT_COUNTER_R50_APPROVED_SHA`: exact approved deployment source SHA
- `BITEVO_EVENT_COUNTER_R50_NOT_BEFORE`: explicit canonical UTC ISO timestamp
- `BITEVO_EVENT_COUNTER_R50_EXPIRES_AT`: exclusive expiry on the same UTC day

The caller supplies `X-BitEvo-R50-Operator-Token` and `X-BitEvo-R50-Trial-Id`.
The existing global ENABLED/PROVIDER_READY and signing-secret conditions still
apply. This candidate neither creates nor modifies those provider settings.
R50 additionally pins the production project, the verified Worker URL, the
source SHA, exact API URL, Origin, disabled browser-source mode and event tuple.
Unknown or incomplete R50 configuration, or R50 headers without its configuration,
cannot fall through to legacy admission. With neither R50 configuration nor
headers, the pre-existing non-R50 contract is unchanged. Do not enable the legacy
public lane to work around an R50 denial.

The observed Worker endpoint used as the R50 pin is:
`https://bitevo-agent-site.mirokonkr.workers.dev/b1-2/event`.
Project: `prj_U2iHyiwhJlO33r0u4uN65PpdzEiv`.
These pins come from R50-A metadata, not from naming conventions. Future execution
must independently revalidate them and the effective deployment state.

## Atomic grant contract and explicit production HOLD

The handler requires a server-supplied `R50GrantStore.consumeOnce` adapter before
operator admission. There is NO production adapter or adapter factory in this
candidate. The exported runtime entry point does not inject one. Consequently,
setting R50 environment variables alone cannot make this candidate send an event.
It returns `R50_NOT_READY` before reading client IP or forwarding.

The adapter must operate against pre-provisioned, approved durable grants. It
must atomically verify policy, expiry and unused/unrevoked state, then consume
one grant for the stable `(project, trialId)` identity across ALL replicas and
restarts. It must NOT create a grant on first use or rearm it after failure.
Token rotation, a source change or extending expiry must not reset the same
consumption key. The separate policy digest binds those values and the exact
receiver and event. The adapter must reject any mismatch, revoked/absent grant
or uncertainty and must never retry an ambiguous consume operation.

The API checks the exact affirmative receipt, rechecks the time window after
consumption and makes at most one downstream attempt for that successful claim.
All negative results and exceptions fail closed. Timeout, malformed downstream
receipt, expiry after claiming and lost claim response do not refund the permit.
Expired/revoked/grant-uncertain denials require inspection, not another event.
An external adapter must also have a bounded I/O deadline; this interface alone
is not proof of its latency, atomicity, durability, revocation or failure semantics.

The in-memory fixture in the unit suite is deliberately a LOCAL ATOMIC MODEL.
Its concurrent-handler tests verify consumer control flow and the contract,
not distributed exactly-once behavior. No Redis, Durable Object, D1 grant table,
rate limiter or local file is silently substituted as production one-shot storage.
The Worker still has no request-ID deduplication. This candidate therefore does
NOT establish exactly-once event accounting or protection against replay of a
captured signed Worker request. Signing material remains server-side.

## OFF and disclosure

Unchanged: `Layout.astro`, `RuLayout.astro`, browser counter and legacy triage
tracker, coverage default `disabled`, Worker/receiver/report configuration,
SQL schema, EN/RU privacy disclosure, package/dependencies and release manifest.
The public browser remains OFF. A later live trial needs a separate bounded
operator/browser integration, a qualified durable grant backend, a truthful
trial disclosure decision and explicit execution/compensation permission.
Setting the global switch OFF prevents further admission; consumed grants must
remain consumed if it is later re-enabled. OFF cannot undo an event already sent.
The local tests verify this behavior; no effective production OFF transition or
D1 effect was performed in R50-B.

cannot be reused as a live trial's immediate before-read. Next implementation
scope must select and qualify durable grant storage and the bounded browser
operator path locally before any request for live deployment or event permission.
